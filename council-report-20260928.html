Council of Five • Deliberation Report

Spotify Continuous Playback Service

Architecture, Spotify API Constraints & Cloud Feasibility Assessment

✓ Recommendation: Proceed with Key Enhancements Unanimous Consensus

The application architecture is viable, robust, and aligned with official Spotify API requirements, provided two critical constraints are addressed in the design:

  • Spotify Connect Target Handling: Spotify Web API is a remote orchestrator, not a headless audio sink. Audio requires an active Spotify Connect target (e.g. phone, smart speaker, or embedded browser player). The service must include explicit device selection and built-in Web Playback SDK support.
  • Free Cloud Resiliency: Free hosting tiers sleep after inactivity. The daemon's internal timer and a self-ping / health-endpoint ensure the service keeps running and automatically recovers after cold starts.
  • Proactive Token Refresh: Rotating OAuth tokens 5 minutes prior to expiry guarantees uninterrupted 24/7 operation.
The One Thing to Do First: Implement the core Node.js server with resilient OAuth 2.0 token rotation, persistent storage, and Spotify Connect device targeting.
Advisor Deliberations (Council of Five)
1. The Contrarian — Failure Modes & Hidden Constraints Critical Risks
  • The "No Active Device" Trap: The official Spotify Web API cannot play into thin air. If the user turns ON the service while all devices are asleep, Spotify returns 404: NO_ACTIVE_DEVICE. The app must handle this gracefully and offer device target selection.
  • Free Hosting Sleeping: Free tiers like Render sleep after 15 minutes without web requests. A background daemon needs an active keep-alive or cron trigger.
  • Rate Limit Caps: Polling more often than every 15-20 seconds risks Spotify 429 throttling. Exponential backoff is mandatory.
2. First Principles Thinker — Fundamental Mechanics System Truths
  • Spotify's API controls existing audio streams; it does not replace audio clients.
  • A rolling OAuth access token (1h life) backed by a stored refresh_token guarantees infinite auth lifespan.
  • Providing dual playback modes (remote Spotify Connect device vs. browser Web Playback SDK) fulfills both 24/7 background usage and immediate local listening.
3. Expansionist — High-Value Enhancements Opportunities
  • "Spotify Minutes" Stream Stats: Show cumulative listening minutes, songs played, and uptime records.
  • Automatic Device Failover: If the primary speaker/device disconnects, failover to an alternative active target.
  • Webhook Alerts: Send Discord or Telegram notifications if an unexpected auth revocation occurs.
4. Outsider — User Experience & Friction Elimination Simplicity
  • Hide all API jargon. Give the user a large power toggle, a playlist link box, and a friendly device dropdown.
  • If devices are asleep, display a helpful message: "Spotify is sleeping. Open Spotify on your phone/speaker or click 'Play Here'".
5. Executor — Sequencing & Implementation Roadmap Execution Plan
  • Phase 1: Node.js backend with Spotify OAuth flow, auto-refresh tokens, and state storage.
  • Phase 2: Watchdog engine with 15s polling, retry backoff, and playlist enforcer.
  • Phase 3: Dark aesthetic dashboard with ON/OFF switch, now playing card, playlist input, and live uptime clock.
  • Phase 4: Dockerfile & deployment documentation for free cloud hosts.
